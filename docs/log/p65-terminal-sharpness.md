## 지시

### 목표

세션 노드 터미널 글자가 흐린 것을 고친다. 사용자의 말: "CLI 창 안에 텍스트가 너무 흐린데 이거 화질 업 못하나? 내가 4k 환경이라 그런지 더 흐리다".

### 할 것

1. **원인 찾기.** 흐림이 어디서 오는지 재서 밝힌다. 의심은 다음과 같다.
   - 판 배율(React Flow viewport의 CSS `transform: scale`)이 xterm이 그린 캔버스(WebGL 또는 DOM)를 늘이거나 줄인다. 100%가 아닌 배율에서는 캔버스 픽셀과 화면 픽셀이 맞지 않는다.
   - 4K 모니터의 Windows 배율(150%, 200%, 175% 같은 분수 배율)에서 `devicePixelRatio`가 분수가 되고, WebGL 글자 아틀라스가 그 값과 맞지 않는다.
   - P45의 창 배율(`setZoom`)과 터미널 글자 배율이 DPR이나 글자 크기를 분수로 만든다.
   - 글꼴(JetBrains Mono, Nanum Gothic Coding), 굵기(500), 줄 높이가 어중간한 픽셀에 걸린다.
   - `will-change: transform` 같은 합성 레이어가 늘이기 전 해상도로 그려진다.
2. **재기.** Electron을 `--force-device-scale-factor=1`, `1.5`, `2`(4K 흉내)로 띄우고, 판 배율 50%·75%·100%·125%와 화면 배율 100%·125%에서 같은 터미널 글을 찍는다. 선명함을 숫자로 견준다(예: 글자 가장자리의 밝기 기울기, 또는 같은 글을 화면 픽셀에 맞춰 그린 기준과의 차이). 바꾸기 전과 뒤를 `experiments/p65/`에 남긴다.
3. **고치기.** 원인에 맞게 고친다. 예를 들면 다음과 같다.
   - 터미널을 판 배율 × DPR에 맞는 해상도로 그린다. 예: 노드 안 터미널 상자를 배율만큼 키우고 글자 크기를 곱한 뒤 역배율로 줄여, 캔버스 픽셀이 화면 픽셀과 1:1이 되게 한다. 확대·축소가 멈춘 뒤에만 다시 그려 움직이는 동안 느려지지 않게 한다.
   - DPR과 글자 크기, 셀 크기를 정수 픽셀에 맞춘다.
   - 레이어를 늘이기 전 해상도로 굳히는 CSS를 없앤다.
   - 지켜야 할 것: 웹처럼 글 고르기와 복사(P38·P42의 배율 보정), 붙여넣기, 휠 스크롤, 셸 기록, WebGL 예산(`RendererBudget`), 먼 배율의 얼굴(요약), 웹 화면(원격)도 같게 동작해야 한다.
4. 판 배율을 바꾸는 동안과 노드가 많을 때(예: 세션 노드 12개) 프레임 시간이 크게 늘지 않는지 잰다.

### 완료 기준

1. 세 DPR(1, 1.5, 2)과 여러 판 배율에서 바꾼 뒤가 바꾸기 전보다 선명하다는 것을 숫자와 스크린숏으로 보인다. 100% 배율·DPR 1에서는 나빠지지 않는다.
2. 고르기·복사·휠·붙여넣기 창 시험(P42·P51의 시험 또는 같은 뜻의 새 시험)이 통과한다.
3. 배율 바꾸기와 노드 12개에서 성능을 전후로 적는다.
4. `cd backend && npm test`, `cd app && npm test`, `cd app && npm run build`가 통과한다.

  - xterm WebGL은 `device-pixel-content-box` 관찰자로 캔버스 픽셀 수를 실제 DPR 기준으로 되돌린다. 처음 고친 판에서는 이 때문에 캔버스가 1.25배 크게 그려졌다. 렌더러의 `_setCanvasDevicePixelDimensions`를 감싸, 바꾼 DPR일 때는 렌더러가 잰 장치 크기를 쓰게 했다.
  - 터미널 요소에 `scale`(캔버스 1픽셀 = 화면 장치 픽셀 1개)과 `translate`(장치 픽셀 경계)를 건다. P47 비율도 이 변환 안에 넣었다.
  - 그래서 터미널이 노드 안에서 차지하는 크기는 칸마다 0.5 장치 픽셀까지 다를 수 있다(남는 곳은 터미널 바탕색). 1:1 칸이 노드 칸보다 크면 내림하고, 내림으로 8%보다 더 작아지면 그 축만 노드를 채운다(조금 늘여 보인다). 셸이 아닌 노드는 오른쪽 여백 안으로 8px까지 넘쳐도 된다. 패널 줄·칸 수는 언제나 배율 1 칸으로 잰다.
  - 캔버스는 한 장 1200만 장치 픽셀, 한 변 8192px까지만 키운다. 넘으면 그만큼만 키우고 나머지는 늘여 보인다.
  - 노드를 끌어 옮긴 뒤의 장치 픽셀 경계는 1초마다 다시 본다.
- 고친 뒤 처음 잰 값에서 배율 100%·DPR 2가 0.80 → 0.90으로 나빠졌다. `getBoundingClientRect`는 Blink가 그릴 때 하는 반올림(변환이 걸린 조상 안의 레이아웃 자리, 캔버스 상자 크기를 장치 픽셀로) 전 값이라, 그 값으로 맞춘 이동이 이미 맞던 자리를 흐트러뜨렸다. 반올림을 계산에 넣자(`paintedAt`, `compensate`의 상자 크기 반올림) 거의 모든 조합이 0.80이 되었다.
- 웹 화면(원격)의 화면 배율은 뿌리의 CSS zoom이라 변환이 아니라 레이아웃 배율이다. 반올림 단위를 CSS px × DPR × zoom으로 했다. 헤드리스 Chromium은 `--force-device-scale-factor`를 무시하고, Playwright의 `deviceScaleFactor` 흉내는 `device-pixel-content-box`가 CSS 크기로 와서(고치기 전에도 캔버스가 CSS 크기) 웹 시험은 DPR 1로만 쟀다.

## 보고

### 만든 것

**1. 원인.** 터미널 글자가 흐린 까닭은 두 가지다(작업 기록에 잰 값).
- 판 배율(React Flow의 CSS scale)이 xterm WebGL 캔버스를 늘이거나 줄인다. 캔버스 픽셀 대 화면 픽셀이 판 배율 그대로였다.
- 분수 DPR(4K 150% 등)이나 창 배율에서는 캔버스가 장치 픽셀 경계 사이에 놓여, 판 배율 100%에서도 반 픽셀씩 번진다.
- DOM 렌더러(WebGL 예산 밖 터미널)는 모든 조합에서 이미 선명했다. 글꼴·굵기·줄 높이·`will-change`는 원인이 아니었다.

**2. 고침(`app/src/renderer/lib/term-sharp.js` 새 파일, `TerminalView.jsx`).**
- 판이 160ms 멈추면 WebGL 터미널마다 xterm이 보는 DPR과 줄 높이를 바꿔, 칸 하나가 화면에서 정수 장치 픽셀이 되게 다시 그린다. 움직이는 동안은 다시 그리지 않는다.
- 터미널 요소에 `scale`(캔버스 1픽셀 = 화면 장치 픽셀 1개)과 `translate`(장치 픽셀 경계)를 건다. Blink의 그리기 반올림(노드 안 레이아웃 자리, 캔버스 상자 크기)과 웹 화면의 CSS zoom을 계산에 넣는다. P47 비율도 이 변환 안에 들어간다.
- 패널 줄·칸 수는 배율 1 칸으로 잰다(`fitDims`). 판 배율을 바꿔도 패널 크기와 셸 기록은 그대로다.
- xterm 내부를 세 곳 쓴다: `_core._coreBrowserService.dpr`(터미널마다 덮음), `_onDprChange`, WebGL `_renderer._setCanvasDevicePixelDimensions`(캔버스 픽셀 수를 실제 DPR로 되돌리는 관찰자를 바꾼 DPR에 맞춤). 없으면 로그를 남기고 예전처럼 그린다.
- 계산은 단위 시험한다(`app/test/p65-lib.test.mjs` 10개).

### 계획과 다른 곳

- 지시의 예("상자를 배율만큼 키우고 글자 크기를 곱한 뒤 역배율로 줄이기")가 아니라 xterm이 보는 DPR을 바꿨다. 글자 크기를 곱하면 0.1px 반올림과 칸 내림으로 줄·칸 수가 흔들리고, DPR을 바꾸면 패널 크기를 건드리지 않고 칸의 장치 픽셀만 정할 수 있다.
- 노드를 꼭 채우기보다 캔버스 1픽셀 = 화면 1픽셀을 먼저 한다. 0.94~0.98배의 작은 늘이기도 판 배율 늘이기만큼 흐렸기 때문이다. 그래서 터미널이 노드 안에서 차지하는 크기가 칸마다 0.5 장치 픽셀까지 다르다(예: DPR 1.5·판 125%에서 칸 높이가 42.5가 아니라 43 장치 픽셀이라 18줄이 9 장치 픽셀 길다).
- 화면 글(사전)과 `styles.css`는 고치지 않았다.

### 알려진 문제

- 판을 움직이는 동안은 예전처럼 늘인 그림이다. 멈추고 160ms 뒤 선명해진다.
- 1:1 칸이 노드에 안 들어가고 내리면 8%보다 작아지는 축은 노드를 채우느라 조금 늘여 보인다(fillX·fillY). 작은 판 배율에서 자주 생긴다(성능 시험의 판 48%: DPR 1에서 칸 너비 3.84 장치 픽셀을 4로 그리고 0.96배로 줄여 보인다). 창 배율 125% × DPR 2의 판 75%·100%(1.10·1.13)도 아직 0.80이 아니다. 까닭은 찾지 못했다.
- 1:1로 그린 터미널은 노드보다 조금 작거나(바탕색이 보인다) 셸이 아니면 오른쪽 여백 안으로 8px까지 클 수 있다.
- xterm 6.0.0·addon-webgl 0.19의 내부를 쓴다. 판을 올리면 `TerminalView.jsx`의 P65 부분을 다시 확인해야 한다.
- 원격 웹 화면은 DPR 1(헤드리스)로만 쟀다. 실제 고해상도 브라우저는 재지 않았다.
- 판 배율마다 xterm 글자 아틀라스를 새로 만든다. 같은 배율의 터미널끼리는 나눠 쓰고, 12노드에서 긴 프레임은 없었다. 메모리는 재지 않았다.

### 고쳐야 할 문서 문장

- ARCH 7.2 가까이 얼굴에 한 항목: 판이 멈추면 WebGL 터미널은 화면 장치 픽셀에 맞춰 다시 그린다(칸 = 정수 장치 픽셀, 캔버스를 장치 픽셀 경계에 맞춤). 패널 줄·칸 수는 배율 1 칸으로 잰다. 그래서 터미널이 노드 안에서 차지하는 크기가 배율에 따라 조금 다를 수 있다.
- ARCH 모듈 표에 `app/src/renderer/lib/term-sharp.js`(판 배율·DPR 아래 터미널을 화면 픽셀에 맞추는 계산) 한 행.
- testing.md 창 시험 절: `p42-select`·`p51-terminal`은 `MT_E2E_BOARD=p65`, `MT_E2E_DPR`(`--force-device-scale-factor`)로 다른 판·DPR에서 돌린다. 분수 DPR 화면 측정은 `capturePage`에 DIP 사각형을 주지 말고 창 전체를 찍어 장치 픽셀로 자른다. 헤드리스 Chromium은 DPR 플래그를 무시하고, Playwright `deviceScaleFactor`는 캔버스 크기 측정에 쓰지 않는다.
