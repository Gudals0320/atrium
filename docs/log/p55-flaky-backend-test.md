## 지시

### 목표

가끔 실패하는 백엔드 시험을 찾아, 시간에 기대지 않게 고친다. 사용자의 말: "이거 작업 ㄱㄱ".

P49 작업자가 본 것(`docs/log/p49-remote-r3-tailscale.md` 보고 "알려진 문제와 위험"): 마지막 확인 때 `cd backend && npm test`가 한 번 1개 실패했고(이름을 남기지 못함), 그 뒤 7번 연달아 모두 통과했다. 시간에 기대는 시험이 가끔 흔들리는 것으로 보았다.

### 할 것

1. **찾기.** `cd backend && npm test`를 여러 번(예: 30번 이상, 기계 부하를 바꿔 가며. 다른 작업자가 도는 지금 상태도 부하다) 돌려, 실패한 시험의 이름과 출력을 모은다. 시험마다 따로 여러 번 돌리거나 `--test-concurrency`를 바꿔 보는 것도 쓴다. 실패가 안 나오면 시간·타이머·포트·임시 폴더·전역 상태에 기대는 시험을 코드로 찾아 의심 목록을 만든다.
2. **원인.** 찾은 시험마다 왜 흔들리는지(실제 시간 대기, 정해진 포트, 서로 같은 임시 경로, 정리되지 않은 타이머·서버, 순서 의존 등) 밝힌다.
3. **고치기.** 가짜 시계·조건 기다리기·빈 포트(0)·시험마다 따로 임시 폴더처럼 시간에 기대지 않는 방법으로 고친다. 시험의 뜻(무엇을 확인하는지)은 바꾸지 않는다. 시험이 아니라 제품 코드의 경쟁 상태(race)가 원인이면 그것을 고친다.
4. **확인.** 고친 뒤 `npm test`를 다시 여러 번(30번 이상) 돌려 모두 통과하는 것을 보이고, 몇 번 돌렸는지와 걸린 시간을 적는다. `cd app && npm test`, `cd app && npm run build`도 통과한다.

### 읽을 파일

- `CLAUDE.md`, `docs/testing.md`
- `backend/test/` 전부(특히 P47~P49, P40·P41의 시험: 서버, 프록시, 타이머, 재연결을 쓰는 것), `backend/package.json`의 test 스크립트

  - `ATRIUM_DATA_DIR=<워크트리>/backend/.dev/data`, `ATRIUM_APP_USERDATA=<워크트리>/backend/.dev/app`

- 대화 목록은 시험 폴더의 대화만 읽는다(`ATRIUM_CLAUDE_PROJECTS`, `ATRIUM_CLAUDE_DESKTOP=none`). 시험 폴더는 `C:\Workspace\mtask-p55-*`처럼 새로 만든다.

### 지킬 것

- `CLAUDE.md`를 따른다. 프로세스는 직접 띄운 것만 PID로 끈다.
- 이 저장소는 공개다. 작업 기록, 시험 코드, 커밋 메시지에 사용자 경로·메일·토큰을 쓰지 않는다. 커밋 전·푸시 전 검사를 건너뛰지 않는다.
- 같은 때 다른 작업자(P54(개발용 판 CLI 오류))가 돈다. 맡은 일에 필요한 만큼만 작게 고친다.
- 자기 브랜치에만 커밋한다. 커밋 메시지에 `Co-Authored-By` 줄을 넣지 않는다. `main`을 바꾸거나 푸시하지 않는다. `node_modules`는 워크트리 안에서 받는다(`npm ci`).
- 문서는 이 작업 파일의 작업 기록 절과 보고 절만 고친다. 고쳐야 할 ARCH·testing 문장이 있으면 보고 절에 짧게 적는다.
- 끝나면 보고 절을 쓰고, 맨 마지막에 `<워크트리>/backend/.dev/p55.done`(브랜치 이름과 마지막 커밋 해시 두 줄)을 만든다.

## 작업 기록

2026-11-05 P55 작업자 세션.

- **그냥 돌리기.** `npm test`(파일 41개, 시험 401개) 30번. 앞 10번 남짓은 CPU를 12개 스레드로 태우는 부하를 함께 걸었다. 30번 모두 통과(부하 없을 때 한 번 약 10초, 부하 아래 약 60초).
- **파일마다 동시에.** 파일 41개를 하나씩, 같은 파일을 16개 프로세스로 동시에 2번씩(파일마다 32번, 모두 1,312번) 돌렸다. 모두 통과. 의심 파일 12개(p4, p8, p18, p21, p22, p24, p29, p40, p41, p47, p49, unit)를 12개씩 따로 한 번 더 돌렸다. 모두 통과.
- **지연 넣기.** 실패가 드물어, 시험 프로세스에 `--import`로 작은 모듈을 미리 불러 이벤트 루프를 가끔(20ms 안팎마다 0~150ms) 막았다(git 밖 임시 폴더). 실제 부하에서 타이머와 I/O가 늦어지는 것을 흉내 낸다. 의심 파일 12개를 12개 동시 × 2번 돌리자 **p41 "모델 오류" 시험이 24번 중 3번 실패**했다. 이어서 파일 41개 모두를 같은 조건(12개 동시 × 2번)으로 돌리자 p7 J3(성능 예산) 한 번 말고는 새 실패가 없었다.
- **코드 읽기.** 고정 대기(`setTimeout(r, n)`), 시간 상한 단언(`Date.now() - t0 < n`), 정해진 포트·이름, 파일이 보이자마자 읽기를 찾아 읽었다. p18 "옛 백엔드 끄기"의 경쟁 상태를 찾았다.

### 찾은 것과 원인

1. **p41 `P41 모델 오류: StopFailure model_not_found나 …`(제품 코드의 경쟁 상태).** 실패 출력: `The input did not match the regular expression /쓰지 못한 모델: haiku/. Input: "There's an issue with the selected model (haiku)."`. `Branch.noteModelError`가 "이미 알린 오류"를 `rt.lastError.at`(밀리초 시각)으로 가렸다. 두 StopFailure가 같은 밀리초에 오면 둘째 오류를 같은 오류로 보고 판 이벤트(`model_error`, 부모의 `branch_child_error`)를 남기지 않는다. 시험은 두 오류 사이에 동기 코드만 있어서, 그 사이가 1ms 안에 끝나면 실패한다. 실제 판에서도 연달아 난 오류 하나를 놓칠 수 있다. 시계를 멈춘(`t.mock.timers`의 `Date`) 시험으로 늘 재현했다(고치기 전 `['first']`, 기대 `['first', 'second']`).
2. **p18 `P18 옛 백엔드 끄기: …`(시험의 경쟁 상태).** 시험이 띄운 가짜 백엔드는 `fs.writeFileSync`로 `backend.json`을 쓴다. 시험은 `fs.existsSync`가 참이 되자마자 `shutdownLegacyBackend`를 불렀다. 파일이 만들어지고 내용이 써지기 전에 읽으면 JSON을 읽지 못해 `{ running: false }`가 되어 `stopped: true` 단언이 실패한다. 같은 모양(자식 프로세스가 쓰고 부모가 보이자마자 읽기)을 따로 재현하니 200번 중 1번 빈 파일을 읽었다. 또 기다리기가 50ms × 100번(5초) 상한이라, 아주 느린 기계에서 자식이 5초 안에 뜨지 못해도 같은 실패가 난다.
3. **p7 J3 `대화가 많아도(2,000개 …) 처음 훑기는 몇 초 안`(성능 예산, 고치지 않음).** 혼자 약 1.8초, 전체 시험 안에서도 수 초다. 20초 상한은 인위적으로 CPU를 거의 다 빼앗은 지연 조건에서만 넘었다(21.3초). 시간 예산 자체가 이 시험의 뜻이라 그대로 두었다.

### 고친 것

- `backend/src/branch.mjs`: `modelErrors`에 시각 대신 알린 오류 객체(`rt.lastError`)를 둔다. 훅마다 새 객체가 생기므로 같은 오류는 한 번, 같은 밀리초의 다른 오류는 각각 알린다. 새 런타임(깨우기, 다시 붙기)은 `lastError`가 `null`에서 시작하므로 다시 알리는 일은 없다.
- `backend/test/p41.test.mjs`: 시계를 멈추고 같은 밀리초에 두 오류를 내는 시험 하나를 더했다(고치기 전에 실패하는 것을 확인).
- `backend/test/p18.test.mjs`: 가짜 백엔드가 임시 파일에 쓴 뒤 이름을 바꿔(`renameSync`) 다 쓴 파일만 보이게 했다. 시험은 `backendInfo`가 읽히고 `/health`가 답할 때까지 조건으로 기다린다(시간 상한 없음. 가짜 백엔드가 먼저 끝나면 그 까닭으로 바로 실패).

## 보고

### 만든 것

- 가끔 실패하던 백엔드 시험 둘을 찾아 고쳤다.
  - p41 모델 오류 시험: 원인은 제품 코드다. 같은 밀리초에 난 두 모델 오류 가운데 둘째를 판 이벤트로 남기지 않았다(`Branch.noteModelError`가 오류를 시각으로 구분). 오류 객체로 구분하게 고쳤고, 시계를 멈춘 재현 시험을 더했다.
  - p18 옛 백엔드 끄기 시험: 가짜 백엔드가 `backend.json`을 다 쓰기 전에 읽을 수 있었다. 다 쓴 파일만 보이게 하고, 파일과 `/health`가 준비될 때까지 조건으로 기다린다.
- P49가 본 실패가 둘 가운데 어느 것인지는 이름이 남지 않아 확정할 수 없다. 지연을 넣은 반복에서 실제로 실패가 나온 것은 p41이다(24번 중 3번).

### 확인

- 고친 뒤 `cd backend && npm test`를 **35번 연달아** 돌려 모두 통과했다(시험 402개, 모두 5분 55초, 한 번 약 10초. 앞쪽 여러 번은 CPU 8개 스레드 부하 아래).
- 같은 지연 조건(이벤트 루프 막기, 12개 동시)으로 p41과 p18을 각 48번 돌려 모두 통과했다(고치기 전 p41은 24번 중 3번 실패).
- `cd app && npm test` 185개 통과, `cd app && npm run build` 통과.
- 개발용 판, herdr, 시험 폴더는 쓰지 않았다. 띄운 것은 시험 프로세스와 CPU 부하 프로세스뿐이고 모두 스스로 끝났다.

### 계획과 다른 곳

- 그냥 반복(30번)과 파일별 동시 실행(1,300여 번)에서는 실패가 나오지 않았다. 이벤트 루프를 막는 지연 주입으로 드러냈다.

### 알려진 문제

- p7 J3(대화 2,000개 처음 훑기 20초 안, 두 번째가 첫 번째보다 빠름)는 시간 예산을 재는 시험이다. 아주 무거운 부하에서는 넘을 수 있다(지연 주입에서 1,000번 가까이 돌려 한 번, 21.3초). 평소 기계에서는 넘지 않을 만큼 여유가 있어 두었다.
- 지연 주입에서도 실패하지 않았지만 실제 시간 상한을 쓰는 시험이 남아 있다: p8 신뢰 관문(25ms × 40번 기다리기, 그 안에 실제 `sleep(150)`), p29 handshake(1초 제한을 5초로 경쟁), p40(`< 1000`, `< 5000`), p47 지연 프록시(`>= 110`ms). 여유가 커서 손대지 않았다.
- 제품 쪽 `backend.json`도 `writeFileSync`로 바로 쓴다(`backend.mjs`). 읽는 쪽(`startBackend` 등)은 읽지 못하면 다시 시도하거나 "꺼짐"으로 보므로 시험을 흔들지는 않는다. 같은 때 P54가 이 근처를 고치고 있어 건드리지 않았다.
- ARCH·testing 문서에 고칠 문장은 없다.
