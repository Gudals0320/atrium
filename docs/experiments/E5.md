# E5. 가까이 보이는 노드 8개에 제어기를 붙였을 때 메모리, CPU, 화면 지연

2026-10-29에 P2 창(`app/`)으로 했다. 결론부터 적으면 **8개를 붙여도 이 PC에서는 부담이 작다.** 제어기 8개가 합쳐 127MB(하나 15.9MB), 창(Electron 프로세스 전체)이 약 420MB를 썼다. 쉬는 동안 CPU는 거의 0이었다. 8개 세션이 동시에 150줄을 출력하는 동안에도, 기록해 둔 한 세션 전체 프레임(135KB)을 8개 터미널에 동시에 쏟아 넣는 동안에도 50ms를 넘는 화면 프레임은 없었다. 입력부터 그 결과 프레임이 창에 오기까지는 중앙값 약 32ms였다.

WebGL 상한과 DOM 대체(BRIEF 위험 2)를 넣었다. WebGL 예산 기본값은 8이고, 넘거나 컨텍스트를 잃으면 DOM으로 그린다. 같은 부하에서 DOM으로 그린 터미널이 섞이면 창 렌더러의 CPU가 약 3배였다(쉬지 않고 넣을 때 36% → 119%). 제어기 상한(기본 8)도 넣었다. 상한을 넘는 노드는 터미널 대신 안내를 보여준다.

## 1. 방법

| 항목 | 값 |
|---|---|
| 창 | P2 창(Electron 45.1.0, xterm.js 6.0.0, `@xterm/addon-webgl` 0.19.0), 창 크기 1600×960, 판 영역 1584×828 |
| 세션 | 개발용 프로필(`multitask-dev`, 포트 47811)의 claude 세션 8개(`--model haiku`), 노드 720×460 |
| 배치 | 8개가 모두 화면 안에 들어오고 가까이 얼굴(화면 너비 360px)이 되는 배율 0.5. 터미널 크기 100×27 |
| 비교 | `webgl8`: WebGL 예산 8(8개 모두 WebGL), `dom4`: 예산 4(`?webglBudget=4`, WebGL 4개 + DOM 4개) |
| 스크립트 | `app/test/e2e/e5.mjs webgl8|dom4`, `app/test/e2e/e5-extra.mjs`(컨텍스트 잃기, 제어기 상한) |
| 원본 | `experiments/p2/e5-webgl8.json`, `e5-dom4.json`, `e5-*.txt`, 스크린숏 `e5-*.png` |

측정 방법:

- **메모리:** 제어기(`herdr terminal session control`), 백엔드 `node`, herdr 서버는 `Get-Process`의 작업 집합(WorkingSet64). 창은 Electron `app.getAppMetrics()`의 작업 집합(Browser = main, Tab = 창 renderer, GPU, Utility).
- **CPU:** 모두 OS 프로세스 시간(`TotalProcessorTime`)의 차이를 걸린 시간으로 나눈 값이다. 한 코어 기준 %다. Electron의 `percentCPUUsage`는 값이 너무 작게 나와 쓰지 않았다.
- **화면 프레임:** 창 안에서 `requestAnimationFrame` 간격. 이 PC 화면은 144Hz라 평소 간격이 6.9ms다. 50ms를 넘는 간격을 "긴 프레임"으로 셌다.
- **쓰기 시간:** 프레임을 받은 때부터 `term.write`의 완료 콜백까지. 프레임이 몰리면 앞 프레임을 기다린 시간도 들어간다.
- **입력 → 프레임:** `terminal.input`으로 Claude Code 입력칸에 `x`를 넣고 지우기(`\x7f`)를 세션마다 5번씩, 보낸 때부터 그 세션의 다음 프레임이 창에 올 때까지. 제출하지 않았다.
- **실제 턴:** `@all`로 "1부터 150까지 한 줄에 하나씩"을 보내고 8개가 모두 working → ready가 될 때까지.
- **합성 부하:** E4에서 기록한 한 세션 전체 프레임(`experiments/e4-frames-fullscreen.json`, 전체 화면 렌더러, 256개, 135KB, 120×40)을 창 안에서 8개 터미널의 프레임 처리기에 동시에 넣었다. 모델 사용량이 들지 않는다. "기록된 시간 간격대로"(약 50초)와 "쉬지 않고" 두 가지다. 끝난 뒤 제어기를 놓았다가 다시 붙여 화면이 herdr 화면과 같아졌는지 보았다.

## 2. 결과

### 2.1 쉬는 상태(제어기 8개 붙음, 10초)

| 항목 | webgl8 | dom4 |
|---|---|---|
| 제어기 8개 메모리 | 127.2MB(하나 15.9MB) | 127.2MB |
| 제어기 CPU | 0% | 0% |
| 창 전체(Electron) | 420MB(Browser 102, GPU 128, Utility 50, Tab 140) | 409MB(Browser 103, GPU 120, Utility 51, Tab 136) |
| 창 CPU | Browser 0.2%, GPU 0.2%, Tab 0% | Tab 0.6% |
| 백엔드 `node` | 68MB, 0.2% | 69MB, 0% |
| herdr 서버 | 34MB, 2.5% | 34MB, 3.8% |
| 화면 프레임 간격 | 중앙값 6.9ms, 최대 7.2ms, 긴 프레임 0 | 같음 |

### 2.2 입력 → 다음 프레임(80번)

| | 중앙값 | p95 | 최대 |
|---|---|---|---|
| webgl8 | 32.5ms | 53.1ms | 90ms |
| dom4 | 32.7ms | 35.0ms | 35.7ms |

E0의 "글 넣기 → 제어기 프레임에 나타남"(Claude Code 입력칸 12ms)보다 길다. 이번 값에는 창 → 백엔드 WebSocket → 제어기 stdin → herdr → Claude Code 다시 그리기 → 제어기 → 백엔드 → 창의 왕복이 모두 들어 있다. 사람이 느끼기 어려운 크기다.

### 2.3 실제 턴: 8개가 동시에 150줄 출력

| 항목 | webgl8 | dom4 |
|---|---|---|
| 8개 모두 끝날 때까지 | 6.0초 | 6.4초 |
| 받은 프레임 | 239개, 40KB(세션당 5.1KB) | 232개, 40KB |
| 쓰기 시간 | 중앙값 0.1ms, 최대 5.5ms | 중앙값 0.1ms, 최대 6.5ms |
| 화면 프레임 간격 | 최대 20.9ms, 긴 프레임 0 | 최대 13.9ms, 긴 프레임 0 |
| 창 CPU | Tab 12.6%, GPU 6.8%, Browser 2.4% | Tab 10.7%, GPU 9.0% |
| 창 메모리 최고 | 429MB | 427MB |
| 제어기 CPU | 거의 0(하나 0.3%) | 0 |
| 백엔드 / herdr 서버 CPU | 3.4% / 22.3% | 4.4% / 19.4% |

**턴 하나의 프레임 양은 PLAN의 기준보다 훨씬 작다.** 150줄을 출력한 턴이 세션당 약 5KB였다. herdr 제어기는 보이는 27줄 화면의 차이분만 보낸다. PLAN 7절 P2의 "턴 하나에 100~135KB"는 E4에서 여러 턴을 돈 한 세션 전체의 프레임 합(256개, 135KB)이었다. 그 양은 아래 합성 부하로 따로 재현했다.

부하는 창보다 herdr 서버에 갔다(약 20%). 8개 세션의 화면 모델을 다시 그려 차이를 만드는 일이다.

### 2.4 합성 부하: 135KB × 8개 터미널(1MB, 2,048프레임)

| 항목 | webgl8, 기록된 간격대로 | dom4, 기록된 간격대로 | webgl8, 쉬지 않고 | dom4, 쉬지 않고 |
|---|---|---|---|---|
| 걸린 시간 | 49.8초 | 49.8초 | **1.75초** | **2.9초** |
| 쓰기 시간 중앙값 / p99 / 최대 | 4.7 / 7.5 / 16ms | 4.8 / 13.6 / 19.6ms | 5.0 / 8.1 / 14ms | 8.4 / 19.4 / 28.5ms |
| 화면 프레임 간격 최대 | 7.2ms | 41.7ms | 13.8ms | 13.9ms |
| 긴 프레임(50ms 넘음) | 0 | 0 | 0 | 0 |
| 창 renderer(Tab) CPU | 9.4% | 11.8% | 35.7% | **119.2%** |
| GPU 프로세스 CPU | 4.1% | 3.3% | 54.4% | 30.7% |
| renderer 메모리 | 149MB | 198MB | 166MB | 235MB |
| 다시 붙인 뒤 화면 | 216줄 중 다른 줄 0 | 0 | | |

- 쉬지 않고 넣을 때 DOM이 섞이면 renderer CPU가 약 3배, 걸린 시간이 약 1.7배, renderer 메모리가 약 70MB 더 늘었다. WebGL은 그 일을 GPU 프로세스로 넘긴다.
- 화면 갱신이 멈추는 일(50ms 넘는 프레임)은 어느 조건에서도 없었다.
- 합성 프레임으로 어지럽힌 화면은 제어기를 놓았다 다시 붙이자 첫 전체 프레임 하나로 herdr 화면과 칸 단위까지 같아졌다(C1과 같은 길).

### 2.5 WebGL 컨텍스트를 잃었을 때

`WEBGL_lose_context`로 한 터미널(a)의 컨텍스트를 일부러 잃게 했다(`e5-extra.mjs`, `experiments/p2/e5-extra.txt`, 스크린숏 `e5-context-lost-dom-fallback.png`).

- xterm WebGL 애드온은 컨텍스트가 돌아오기를 3초 기다린 뒤 `onContextLoss`를 낸다. 창은 그 애드온을 버리고 DOM으로 그린다. 결과: a의 렌더러가 `dom`, WebGL 예산 사용 8 → 7, a의 DOM 줄 27개, 8개 터미널 216줄 모두 herdr 화면과 같음. 입력도 그대로 됐다.
- 네 번 중 세 번은 위와 같았다. **한 번은 컨텍스트를 잃은 뒤 8개 터미널이 모두 놓였다**(예산 사용 0, 그 뒤 입력이 `not attached`로 거부). 창 로그에 오류는 남지 않았고 다시 나오지 않아 원인을 찾지 못했다(`experiments/p2/e5-extra-detached-once.txt`). 조사용 반복 실행 기록은 `e5-probe-ctxloss.txt`다.

### 2.6 제어기 상한

`?maxControllers=6`으로 8개 노드를 가까이 얼굴로 띄웠다(`e5-max-controllers-6.png`). 화면 가운데에 가까운 6개에만 제어기가 붙었고(백엔드 `relay` 6개), 나머지 2개(f, h)는 "화면 스트림 상한을 넘어 터미널을 붙이지 않았다"는 안내와 마지막 답을 보여주었다.

## 3. 해석

- 가까이 보이는 노드 하나의 비용은 제어기 약 16MB와 창 쪽 WebGL 터미널 하나다. 8개는 이 PC에서 문제가 되지 않는다. 판 전체의 큰 비용은 화면이 아니라 claude 프로세스 자체다(BRIEF 6절: 36개에 약 9.9GB).
- 실제 턴의 프레임은 작고(세션당 수 KB), 턴 중 부하는 herdr 서버에 간다. 많은 세션이 동시에 출력할 때는 herdr 서버 CPU를 본다.
- DOM 대체는 동작하지만 비싸다. 예산을 8보다 크게 올리기보다, 상한을 넘는 노드는 터미널을 붙이지 않고 중간·멀리 얼굴로 보이는 지금 방식이 낫다.
- 제어기 상한과 WebGL 예산을 같은 값(8)으로 두면, 정상일 때는 DOM 터미널이 생기지 않는다. DOM은 컨텍스트를 잃었을 때의 대체 수단으로만 쓰인다.

## 4. 확인하지 않은 것

- 터미널을 하나도 붙이지 않은 창의 기준 메모리. 그래서 "터미널 하나당 창 메모리"는 따로 구하지 않았다.
- 16개처럼 상한보다 많이 붙인 경우, 여러 모니터, 낮은 사양 PC
- 컨텍스트를 잃은 뒤 모든 터미널이 놓인 한 번의 원인(2.5)
- 노드가 많을 때(수십 개) React Flow 자체의 부담. 이번 판에는 노드가 8개였다.

## 5. 계획에 반영할 것

1. PLAN 7절 P0 표의 E5: "끝남. 8개에서 제어기 127MB, 창 약 420MB, 긴 프레임 0. WebGL 예산 8과 제어기 상한 8을 기본값으로"로 바꾼다.
2. PLAN 7절 P2의 "턴 하나에 100~135KB인 프레임 양": 실제 턴은 화면 차이분이라 세션당 수 KB(150줄 출력 턴에 5KB)였다. 100~135KB는 한 세션 전체 기록이다. 문구를 고친다.
3. PLAN 8절 열린 결정 "동시 실행 상한과 제어기 상한의 기본값": 제어기 상한 8을 기본값으로 정한다. 동시 실행 상한은 그대로 열어 둔다.
4. BRIEF 6절 위험 2: 결과(WebGL 예산 8, DOM 대체 동작, DOM은 약 3배 비쌈, 제어기 상한 8)를 적는다.
5. 컨텍스트 손실 뒤 모든 터미널이 놓인 한 번(2.5)은 P3에서 다시 본다. 노드마다 오류 경계(React error boundary)를 두어 한 노드의 오류가 판 전체로 번지지 않게 하는 것을 제안한다.
