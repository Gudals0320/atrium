# E0. herdr 소켓 API만으로 multitask를 무한 캔버스 클라이언트로 만들 수 있는가

2026-10-29에 했다. 결론부터 적으면 **네 가지 모두 된다.** herdr 0.9.5의 소켓 API만으로 (1) 새 `claude` 세션을 시작하고, (2) 상태 이벤트로 working, 내 답 필요(blocked), 끝남(idle 또는 done)을 구분하고, (3) 터미널 화면을 실시간으로 그리고, (4) 글을 보내 제출할 수 있었다. 단 (3)은 소켓 API가 아니라 herdr CLI의 보조 통로(`terminal session observe`/`control`)로 받아야 한다. 소켓 API는 화면 스냅샷(`pane.read`)만 주고 출력 스트림은 주지 않는다.

**추천: herdr 클라이언트로 만든다.** 조건은 6절에 적었다.

## 1. 환경과 격리

| 항목 | 값 |
|---|---|
| herdr | 0.9.5(stable), 소켓 프로토콜 22, `%USERPROFILE%\.herdr\packages\standalone\releases\0.9.5-x86_64-pc-windows-msvc\herdr.exe` |
| Claude Code | 2.1.312 |
| Node | 24.19.0. 소켓 클라이언트는 Node `net`만 썼다. 화면 모델은 `@xterm/headless` 5.5.0 |
| 시험 폴더 | `experiments/proj`(저장소에서 무시, 이미 신뢰한 폴더라 시작 대화상자가 뜨지 않았다) |
| 스크립트 | `experiments/e0.cjs`(본 실험), `e0-probe2.cjs`, `e0-probe3.cjs`, `e0-probe4.cjs`(보조), `e0-analyze.cjs`. 원본 결과는 `experiments/e0-result.json`, `e0-run.log` |

격리는 **이름 있는 herdr 세션**으로 했다. `herdr --session multitask-e0 server`로 띄우면 서버 프로세스, 소켓, 작업 공간, 패널, 상태 파일이 모두 `%APPDATA%\herdr\sessions\multitask-e0\` 아래에 따로 생긴다. 실험 시작 때 사용자의 기본 세션 서버는 돌고 있지 않았고(`herdr status`: not running), 끝까지 건드리지 않았다. 끝난 뒤 `herdr --session multitask-e0 server stop`과 `herdr session delete multitask-e0`로 서버와 세션 폴더를 지웠다. 띄운 `claude`는 모두 `/exit`로 끝냈고, 남은 `herdr.exe`와 `claude.exe`가 없는 것을 PID 목록으로 확인했다.

두 가지 손질이 필요했다.

- **서버 환경 변수:** herdr 서버는 띄운 셸의 환경을 그대로 물려받고, 패널의 셸과 그 안의 `claude`가 또 물려받는다. 이 실험은 Claude Code 세션 안에서 돌렸기 때문에 처음 띄운 서버에는 `CLAUDE_CODE_CHILD_SESSION` 같은 표시가 들어 있었다(E1 3.2절의 문제가 그대로 생긴다). `env -u ...`로 그 변수들을 뺀 뒤 서버를 다시 띄웠다. `agent.start`에는 `env` 인자가 없고 `workspace.create`에는 있어서, hook용 토큰은 작업 공간을 만들 때 넘겼다.
- **사용자 settings의 herdr hook:** 사용자의 `~/.claude/settings.json`에는 herdr가 설치한 SessionStart command hook(`herdr-agent-state.ps1`)이 있다. 이 hook은 `HERDR_ENV`, `HERDR_PANE_ID`, `HERDR_SOCKET_PATH`를 보고 **자기 패널이 속한 서버**에 세션 ID를 보고하므로, 격리 세션에서 띄운 `claude`의 보고는 격리 서버로만 갔다. 보고 내용은 세션 ID와 대화 기록 경로뿐이고 상태(working 등)는 보고하지 않는다. Claude Code의 상태는 herdr가 **화면을 읽어서** 판정한다(3절).

## 2. 전송 방식

- Windows에서는 **이름 있는 파이프**다. 파이프 이름은 소켓 경로를 그대로 붙인 `\\.\pipe\C:\Users\...\herdr.sock`이다. `herdr.sock` 파일 자체는 `pid:nonce` 한 줄짜리 표시 파일이다. Node `net.connect(파이프 이름)`으로 바로 붙는다.
- 줄 단위 JSON(`{"id","method","params"}` → `{"id","result"}` 또는 `{"id","error":{"code","message"}}`).
- **요청 하나마다 연결 하나다.** 서버가 응답 뒤 연결을 닫고, 한 연결에 요청 두 개를 이어 쓰면 응답이 하나만 온다. `events.subscribe`만 연결을 열어 둔다.
- `ping` 응답에 버전, 프로토콜 번호, 기능 목록(`capabilities`)이 온다. 클라이언트가 붙을 때 호환을 확인할 수 있다.

| 측정(500회) | 최소 | 중앙값 | p90 | p99 | 최대 |
|---|---|---|---|---|---|
| 연결+`ping`+응답+닫기 | 0.28ms | 0.37ms | 0.45ms | 0.64ms | 102.9ms(첫 회) |

PLAN 2.1의 지속 연결 왕복 0.036ms보다 10배 느리지만, 화면 한 프레임(16ms)보다 40배 짧다. 요청마다 연결을 새로 여는 비용은 문제가 아니다.

## 3. 결과

### 3.1 새 claude 세션 시작

```
workspace.create { cwd, label, env }  → 43ms, 작업 공간 w1과 루트 패널 w1:p1(셸: Windows PowerShell 5.1)
agent.start { name, kind: "claude", pane_id, args: ["--session-id", uuid, "--no-chrome", "--permission-mode", "manual", "--settings", path] }
```

- `agent.start`는 12.6ms 만에 `launch_pending: true`로 돌아왔다. herdr는 패널 셸에 `claude --session-id ... --settings ...` 명령줄을 넣는 방식으로 띄운다(응답의 `argv`에 그대로 보인다). 즉 `claude`가 PATH에 있어야 하고, `claude`가 끝나면 패널은 셸로 돌아가며 패널 자체는 남는다(`pane_exited`가 오지 않는다).
- 그 뒤 이벤트: `pane_agent_detected(agent: claude)` +671ms, 첫 `idle` 상태 이벤트 +4,090ms. 보조 실험에서 `agent.wait(until idle|done)`은 3,620ms에 풀렸다.
- `agent.get`의 `agent_session`에 우리가 넘긴 UUID가 들어왔다(사용자 settings의 herdr hook이 보고). herdr는 서버를 다시 시작할 때 이 값으로 `claude --resume`을 한다(문서). 판의 C2 복구에 그대로 쓸 수 있다.
- `--settings`로 넘긴 http hook은 E2와 같이 동작했다(20개 수신, 모두 토큰 일치). SessionStart http hook은 여전히 오지 않는다.

### 3.2 상태 이벤트

구독 `{"type": "pane.agent_status_changed", "pane_id"}`로 받았다. 이벤트 이름은 구독 응답에서는 `pane.agent_status_changed`(점)이고, 수명 주기 이벤트는 `pane_updated`, `pane_agent_detected`(밑줄)이다. herdr 상태는 `idle | working | blocked | done | unknown` 다섯 가지다.

hook(E2 방식, 기준 시각) 대비 herdr 상태 이벤트의 지연이다. 턴 네 개, UserPromptSubmit hook 도착을 0으로 둔다.

| 턴 | working 이벤트 | 막힘 hook(PermissionRequest) → blocked 이벤트 | Stop hook → idle 이벤트 |
|---|---|---|---|
| T1 영문 한 줄(글 넣기+Enter) | +310ms | - | +1,321 → +1,615 (294ms 뒤) |
| T2 AskUserQuestion | +229ms | +1,852 → +2,137 (285ms 뒤) | +36,388 → +36,497 (109ms 뒤) |
| T3 한글(`agent.prompt --wait`) | +277ms | - | +1,425 → +1,583 (158ms 뒤) |
| T4 PowerShell 권한 요청 | +241ms | +1,719 → +1,849 (130ms 뒤) | +37,096 → +37,205 (109ms 뒤) |

- **working:** 제출 뒤 0.23~0.31초. 판정 근거는 OSC 제목의 스피너 글자(규칙 `osc_title_working`)다.
- **blocked(내 답 필요):** AskUserQuestion 선택 화면(규칙 `live_blocked_form`)과 도구 권한 요청(규칙 `bash_permission_prompt`, `generic_permission_prompt`) 둘 다 잡았다. hook보다 0.13~0.29초 늦다. `agent.explain`으로 어떤 규칙이 맞았는지 볼 수 있다. 다만 herdr는 **무엇을 묻는지는 주지 않는다**(`state_labels` 비어 있음). 질문 글, 선택지, 도구 이름과 명령은 E2의 hook(`PreToolUse`, `PermissionRequest`)으로 받아야 한다.
- **끝남:** Stop hook 뒤 0.11~0.29초에 `idle`. 답한 뒤 `working` 재진입은 PostToolUse hook과 비슷한 시점(+243ms, -241ms)이다.
- **done과 idle:** 본 실험에서는 늘 `idle`이었다. 격리 서버에는 패널이 하나뿐이라 그 패널이 항상 "초점"이고, herdr는 초점 패널의 완료를 "본 것"으로 친다. 보조 실험에서 다른 작업 공간에 초점을 두고 턴을 돌리자 `working` → `done`(+1,903ms)이 왔고, `pane.read`로 읽어도 `done`이 유지됐으며, `agent.focus`를 부르자 `idle`로 바뀌었다. 즉 herdr의 `done`은 "검토 대기(unseen)"와 같은 뜻이고, 판이 세션을 본 시점에 `agent.focus`를 부르면 herdr와 맞출 수 있다. 판이 자체 "봤음" 기록을 두는 것(PLAN 3절)과 겹치므로 둘 중 하나를 고른다.
- 막힌 상태에서 `agent.prompt`를 부르면 `agent_blocked` 오류로 거부된다(입력을 넣지 않는다). PLAN B1의 "waiting이면 보내지 않는다" 규칙을 herdr가 이미 한다.
- `/exit` 뒤: SessionEnd hook +376ms, `pane_agent_detected(released: true, final_status: idle)` +1,182ms, 상태 `unknown` +1,484ms. `agent.list`에서 빠진다.
- 보지 못한 것: 오류(StopFailure)와 속도 제한. herdr 상태에는 error가 없다. 이것은 hook으로 받는다.

### 3.3 터미널 화면

**소켓 API에는 출력 스트림이 없다.**

- `pane_output_changed` 이벤트는 스키마에 있지만 구독 목록에 없고, `events.wait`로 걸면 `unsupported_event_wait_match: events.wait currently supports pane agent status matches`가 온다.
- `pane.output_matched` 구독은 "맞는 첫 줄이 바뀔 때"만 한 번씩 온다(모든 글자에 맞는 정규식을 걸어도 처음 1회). 글을 넣고 그 글이 이벤트로 오기까지 중앙값 59ms(5~102ms)로, 폴링이다. 출력 알림 통로로는 쓸 수 없다.
- `pane.read { source: "visible", format: "ansi" }`는 화면 전체를 준다. 120×40 Claude Code 화면이 1,538바이트, 왕복 중앙값 0.84ms(글자만은 1,133바이트, 1.14ms). 이 ANSI 스냅샷을 `@xterm/headless`에 넣자 글자 읽기 8줄이 8줄 모두 같았다. 즉 스냅샷을 그리는 것은 된다. 그러나 언제 다시 읽을지 알려 주는 신호가 없다.

**보조 통로(herdr CLI)로는 된다.** `herdr --session <이름> terminal session observe <pane> --cols 120 --rows 40`을 자식 프로세스로 띄우면 stdout으로 줄 단위 JSON 프레임이 온다.

```json
{"type":"terminal.frame","seq":1,"full":true,"width":120,"height":40,"encoding":"base64","bytes":"G1s/MjAy..."}
```

- 첫 프레임은 전체 화면(`full: true`), 그 뒤는 차이분이다. 쉬는 동안 5초에 0프레임. 턴 하나에 13~103프레임, 2.7~31KB.
- 글 넣기(`pane.send_text`) → 그 글이 든 프레임 도착: Claude Code 입력칸에서 **12ms**(T1). 셸 패널에서 화면 모델에 글자가 보일 때까지 50회: 중앙값 46ms(45~48ms, PowerShell 입력 처리 포함). E1의 node-pty 직접 방식 62ms와 같은 급이다.
- 관찰기는 `herdr.exe` 프로세스 하나(실측 16.8MB)이고 여러 개가 같은 패널을 볼 수 있다. 문서의 "Direct terminal attach는 Windows 미지원"은 TUI 붙이기(`terminal attach`) 얘기이고, observe와 control은 Windows에서 돌았다.
- **제어기**(`terminal session control <pane> --takeover --cols 80 --rows 20`)는 같은 프레임을 주면서 stdin으로 줄 단위 JSON 명령을 받는다. `{"type":"terminal.input","text":"..."}`로 넣은 입력이 30ms 뒤 프레임에 반영됐고, 연결 때 준 80×20이 실제 PTY 크기가 됐다(셸이 `80x20`으로 보고). `{"type":"terminal.resize","cols":100,"rows":30}`도 바로 반영됐다. 제어기는 한 번에 하나이고, 놓으면(`terminal.release`) 크기는 마지막 값으로 남는다. 판의 노드마다 크기가 다른 무한 캔버스에는 이 제어기가 필요하다. 소켓 API의 `pane.resize`는 herdr 탭 레이아웃 안의 분할 비율만 바꾼다.

### 3.4 글 보내기와 제출

| 방법 | 결과 |
|---|---|
| `pane.send_text` + `pane.send_keys ["enter"]` | 각각 1.3ms, 1.1ms에 응답. Enter 뒤 71ms에 UserPromptSubmit hook. E1(216ms에 기록 파일 반영)과 같은 급 |
| `agent.prompt { target, text }` | 322ms에 응답(글과 Enter를 괄호 붙여넣기 모드에 맞춰 한 요청으로 보낸다). UserPromptSubmit hook은 요청 시작 뒤 345ms |
| `agent.prompt { ..., wait: { timeout_ms } }` | 턴이 끝나 `idle`이 될 때까지 기다렸다가 1,928ms에 응답(Stop hook 1,425ms) |
| 한글 | `agent.prompt`로 보낸 한글 문장이 UserPromptSubmit hook의 `prompt`에 글자 하나 다르지 않게 들어왔고, 답도 그대로였다 |
| 막힌 상태에서 답하기 | `agent.send_keys { keys: ["enter"] }` 1~14ms. 27ms 뒤 PostToolUse hook |

`pane.send_input { text, keys }`도 있어 글과 키를 한 요청에 넣을 수 있다. 여러 줄과 수 KB 글은 E3에서 본다.

### 3.5 정리와 닫기

`workspace.close`는 22.5ms, `workspace_closed` 이벤트 23ms. 닫은 뒤 `session.snapshot`은 비어 있었다. 서버 로그에는 패널을 닫을 때 `PaneDied for unknown pane` WARN이 네 번 있었고 다른 경고는 없었다.

## 4. herdr가 주는 것과 주지 않는 것

PLAN 5절의 P1 모듈 기준이다.

| P1 모듈 | herdr 클라이언트일 때 |
|---|---|
| 세션 관리자(PTY, 입력, 크기, 종료, PID) | herdr가 한다. `workspace.create` → `agent.start`, 크기는 제어기, 종료는 `/exit` 뒤 `pane.close`. PID는 `pane.process_info` |
| 실행 계획(`--session-id`, `--settings`, 토큰) | 그대로 필요. 토큰은 `workspace.create`의 `env`로 |
| hook 수신기 | **그대로 필요.** 질문 글, 선택지, 도구 이름과 명령, 마지막 답, 오류 종류는 herdr가 주지 않는다 |
| 상태 계산기 | 둘을 합친다. 패널 수준의 진실은 herdr 상태(화면 판정, 0.1~0.3초 지연), 상세와 error는 hook |
| 화면 모델(@xterm/headless) | 보이는 노드만 관찰기/제어기 프로세스를 붙여 프레임을 xterm.js에 바로 넣는다. 보이지 않을 때는 `pane.read`로 요약 |
| 대화 기록 읽기 | 그대로 필요 |
| 전달 대기열 | 규칙 1(살아 있을 때만), 2(막히면 거부)는 `agent.prompt`가 한다. 3(사용자 입력 중이면 보류)과 취소는 판이 한다 |
| 저장소(SQLite) | 판 배치, 봤음, 메모, 전달 기록만. 세션 등록부는 `session.snapshot`이 대신한다 |
| API 서버와 `mtask` CLI | 판 전용 기능만. 세션 조작은 `herdr` CLI가 이미 있다 |
| git 조사, 자원 감시 | 그대로 필요 |

덤으로 오는 것: 화면을 껐다 켜도 세션이 사는 것(C1), 서버 재시작 때 `claude --resume`(C2의 핵심), 워크트리와 SSH 원격 패널, 사용자가 **이미 herdr 안에서 돌리고 있는 세션**을 같은 API로 판에 올릴 수 있는 것. 데스크톱 앱 세션은 못 올리지만 herdr 세션은 올릴 수 있다.

## 5. 위험

1. **화면 스트림이 공개 API 밖이다.** 관찰기/제어기는 CLI 보조 통로이고 0.9.x에서 바뀔 수 있다. 노드마다 `herdr.exe` 하나(약 17MB)가 붙는다. 보이는 노드 8개면 약 140MB. herdr TUI 자체가 쓰는 클라이언트 프로토콜(`herdr-client.sock`)은 문서가 없다.
2. **상태가 화면 판정이다.** 모르는 대화상자는 `idle`로 떨어진다(문서가 명시). hook을 같이 쓰면 보완된다.
3. **크기와 레이아웃이 herdr 것이다.** 패널 크기는 herdr 탭 레이아웃이 정하고, 제어기 하나만 덮어쓸 수 있다. herdr TUI를 같은 세션에 붙이면 크기가 서로 다툴 수 있다. 판 전용 이름 있는 세션을 쓰면 피할 수 있지만, 그러면 "이미 돌리는 세션 올리기"는 기본 세션에 두 번째로 붙는 형태가 된다.
4. **버전.** herdr는 0.9.5이고 스키마는 `herdr api schema --json`으로 뽑을 수 있다. 소켓 API의 호환 약속은 문서에 없다(TUI 클라이언트 프로토콜만 "endpoint generation"으로 약속). `ping`의 프로토콜 번호로 붙을 때 확인하고 버전을 고정한다.
5. **환경 변수.** 서버가 환경을 물려주므로 판이 서버를 띄울 때 환경을 깨끗이 해야 한다. 사용자가 손으로 띄운 서버에 붙을 때는 판이 제어할 수 없다.
6. **요청마다 연결.** 0.37ms라 성능 문제는 아니지만, 짧은 시간에 수천 번 부르는 설계는 피한다.

## 6. 추천

**herdr 클라이언트로 만든다.** 근거는 네 가지 확인이 모두 됐고, 지연이 직접 만든 백엔드(E1, E2)와 같은 급이며, P1에서 가장 큰 덩어리(PTY 소유, 화면과 무관한 수명, 복구)가 이미 있고, 사용자가 이미 herdr에서 세션을 돌리고 있다는 점이다.

조건:

1. **화면은 제어기/관찰기 프로세스로 받는다.** 가까이 얼굴(xterm.js) 노드만 `terminal session control`(크기를 정해야 하므로)을 붙이고, 멀어지면 놓는다. 중간과 멀리 얼굴은 `pane.read`와 대화 기록으로 그린다.
2. **hook 수신기는 그대로 둔다.** herdr 상태는 패널의 진실로, hook은 상세와 error로 쓴다. 둘이 어긋나면(예: herdr idle인데 hook은 waiting) 화면에 추정 표시를 한다.
3. **판 전용 이름 있는 세션**(예: `herdr --session multitask`)을 판이 깨끗한 환경으로 띄운다. 사용자의 기본 세션은 처음에는 읽기 전용으로 올린다(E1 시나리오와 같은 수준).
4. **API 초안(PLAN 6절)의 이름은 유지한다.** `session.spawn`은 `workspace.create`+`agent.start`로, `session.send`는 `agent.prompt`로, `terminal.attach`는 제어기로 구현한다. herdr에서 떠나야 할 때 판 코드가 아니라 어댑터만 바꾼다.
5. **herdr 버전을 고정**하고, 붙을 때 `ping`의 `protocol`과 `capabilities`를 확인한다.
6. **BRIEF "정한 것" 표**의 "프로세스 구조"와 "기반" 줄을 고친다. 이 문서는 그 전 단계라 BRIEF와 PLAN은 고치지 않았다.

E3(여러 줄·긴 글·한글 입력 방식)과 E9(승인 카드 키 입력)는 herdr 위에서 `agent.prompt`, `pane.send_input`, `agent.send_keys`로 다시 한다. E4(화면 모델)는 제어기 프레임을 xterm.js에 넣는 것으로 범위가 바뀐다. E7(강제 종료 때 자식 프로세스)은 herdr 서버 기준으로 다시 본다.
