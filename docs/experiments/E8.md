# E8. SQLite를 Node 24 내장 모듈(`node:sqlite`)로 쓸지, 별도 패키지로 쓸지

2026-10-29에 했다. 결론부터 적으면 **`node:sqlite`를 쓴다.** Node 24.19.0에서 플래그 없이 불러와지고 경고도 찍히지 않는다. 판에 필요한 기능(WAL, JSON 함수, STRICT 표, `RETURNING`, FTS5)이 모두 있다. 속도는 비교 대상인 better-sqlite3 13.0.3과 같은 급이거나 조금 빠르다. 두 프로세스가 같은 파일을 동시에 써도 막힘이 없었고, 쓰는 중에 강제 종료한 뒤에도 파일이 깨지지 않았다. 설치할 것이 없고 네이티브 바이너리도 없어서 배포와 업데이트가 단순하다. 다만 Node 문서에서 이 모듈은 아직 실험 단계라 API가 바뀔 수 있다. 그래서 SQL과 `node:sqlite` 호출은 저장소 모듈 하나에만 두고, Node 주 버전을 24로 고정한다.

## 1. 방법

| 항목 | 값 |
|---|---|
| Node | 24.19.0(내장 SQLite 3.53.3) |
| 비교 패키지 | better-sqlite3 13.0.3(SQLite 3.53.4). 저장소 밖 스크래치 폴더에 따로 설치했다 |
| DB 파일 | OS 임시 폴더 아래 새 폴더(`mtask-e8-*`). 끝난 뒤 지웠다 |
| 설정 | `journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 2000`. 표는 판의 이벤트 기록과 같은 모양(`id, t, session_id, kind, data`, STRICT, `session_id, id` 색인) |
| 스크립트 | `experiments/e8.cjs`. `node e8.cjs [better-sqlite3 설치 폴더]`. 원본 결과는 `experiments/e8-result.json` |

두 구현에 같은 시험을 돌렸다.

1. 불러올 때 stderr에 경고가 찍히는지
2. 기능: `json_extract`, `jsonb`, FTS5, `RETURNING`, STRICT 표의 형 검사, 한글·이모지 왕복
3. 속도: 자동 커밋 삽입 2,000건, 트랜잭션 하나에 삽입 50,000건, `synchronous = FULL` 자동 커밋 500건, 세션별 최근 50건 조회 1,000회. 행 하나는 hook 본문 모양의 JSON 약 400바이트다
4. 동시 사용: 자식 프로세스 셋(쓰기 둘, 읽기 하나)이 같은 파일을 2초 동안 쓴다
5. 강제 종료: 자식 프로세스가 쉬지 않고 쓰는 중에 0.6초 뒤 그 PID만 `taskkill /F`로 끄고, 다시 열어 `integrity_check`를 본다

## 2. 결과

### 2.1 불러오기와 설치

| 항목 | `node:sqlite` | better-sqlite3 13.0.3 |
|---|---|---|
| 설치 | 필요 없음 | `npm install`. 13.x는 N-API 프리빌드(`prebuilds/win32-x64.node`)를 패키지에 넣어 두어 빌드 도구 없이 불러온다 |
| 불러올 때 경고 | 없음(stderr 빈 글) | 없음 |
| 실험 단계 표시 | `node --help`에 `--no-experimental-sqlite`가 있다. 기본으로 켜져 있지만 아직 실험 기능이라는 뜻이다 | 해당 없음 |
| DB 열기(스키마 포함) | 4.9ms | 13.5ms |

- 비교를 위해 먼저 설치한 better-sqlite3 12.11.1은 npm 12가 설치 스크립트(`prebuild-install || node-gyp rebuild`)를 막아 바이너리 없이 설치됐다. 13.x로 올리고 `npm install-scripts approve`를 하자 동작했다. 패키지를 쓰면 이런 설치 단계가 배포 경로에 들어온다.

### 2.2 기능

두 구현 모두 같았다.

| 기능 | 결과 |
|---|---|
| `json_extract(?, '$.a.b')` | 5 |
| `jsonb()` | 됨 |
| FTS5 | 됨(한글 문서를 넣고 영어 낱말로 찾았다) |
| `INSERT … RETURNING id` | 됨 |
| STRICT 표의 INTEGER 칸에 글 넣기 | 거부됨 |
| `run()` 결과 | `{ changes, lastInsertRowid }`, 둘 다 number |
| 한글·이모지·일본어 왕복 | 같음 |

다른 점은 두 가지다. `node:sqlite`가 돌려주는 행은 프로토타입이 없는 객체(`Object.create(null)`)다. `JSON.stringify`와 구조 분해는 그대로 되지만 `row.hasOwnProperty` 같은 메서드는 없다. better-sqlite3의 `db.transaction(fn)` 같은 트랜잭션 도우미도 없어서 `BEGIN`·`COMMIT`·`ROLLBACK`을 감싸는 작은 함수를 직접 둔다.

### 2.3 속도

단위는 ms다.

| 측정 | `node:sqlite` | better-sqlite3 |
|---|---|---|
| 자동 커밋 삽입 2,000건, 한 건 중앙값 / p99 | 0.017 / 0.066 | 0.025 / 0.084 |
| 트랜잭션 하나에 50,000건 | 172 | 230 |
| `synchronous = FULL` 자동 커밋, 한 건 중앙값 / p99 | 0.29 / 0.49 | 0.33 / 0.51 |
| 세션별 최근 50건 조회, 중앙값 / p99 | 0.029 / 0.126 | 0.024 / 0.116 |

판이 쓰는 양(hook 이벤트가 세션마다 초당 몇 건)에 비해 둘 다 여유가 크다. `synchronous = NORMAL`이면 한 건이 0.02ms 안팎이라 hook마다 바로 써도 된다.

### 2.4 두 프로세스 동시 사용(2초)

| 구현 | 쓰기 1 | 쓰기 2 | 읽기(중앙값 / p99) | busy 오류 |
|---|---|---|---|---|
| `node:sqlite` | 25,485건 | 16,605건 | 8,627회(0.009 / 2.0ms) | 0 |
| better-sqlite3 | 22,161건 | 20,805건 | 5,615회(0.008 / 2.5ms) | 0 |

WAL과 `busy_timeout = 2000`으로 쓰기 둘이 서로 기다리며 번갈아 썼고 오류가 없었다. 판에서는 백엔드 하나만 DB를 쓰지만, 백엔드를 다시 시작하는 순간 이전 프로세스와 새 프로세스가 잠깐 겹칠 수 있다. 그때도 막히지 않는다.

### 2.5 쓰는 중 강제 종료

| 구현 | 끈 뒤 남은 파일 | 다시 연 뒤 `integrity_check` | 남은 행 |
|---|---|---|---|
| `node:sqlite` | `.db` 13.2MB, `.db-wal` 4.1MB, `.db-shm` | ok | 28,178 |
| better-sqlite3 | `.db` 11.8MB, `.db-wal` 4.1MB, `.db-shm` | ok | 25,132 |

다시 열 때 WAL이 자동으로 반영됐고 파일은 깨지지 않았다. `synchronous = NORMAL`에서는 OS나 전원이 함께 꺼질 때 마지막 커밋 몇 건을 잃을 수 있다(SQLite 문서의 설명이고, 이 실험에서는 프로세스만 껐다). 판의 기록(배치, 봤음, 전달, 이벤트)은 그 정도 손실을 견딘다.

## 3. 판단

| 기준 | `node:sqlite` | better-sqlite3 |
|---|---|---|
| 설치·배포 | 없음 | npm 패키지와 네이티브 바이너리. npm 12에서는 설치 스크립트 승인이 필요할 수 있다 |
| Electron | 백엔드는 따로 도는 Node 24 프로세스라 영향 없음 | N-API 프리빌드라 Electron에서도 다시 빌드할 필요는 없을 것으로 보인다(확인하지 않음) |
| 기능 | 필요한 것 모두 있음 | 같음. 트랜잭션 도우미가 더 있음 |
| 속도 | 같은 급이거나 조금 빠름 | 같은 급 |
| 안정성 약속 | 실험 단계. API가 바뀔 수 있음 | 안정 |

설치할 것이 없다는 점이 가장 크고, 기능과 속도에서 잃는 것이 없다. 실험 단계라는 위험은 다음으로 줄인다.

1. `node:sqlite` 호출과 SQL은 저장소 모듈 하나에만 둔다. 바뀌면 그 모듈만 고친다. 그때 better-sqlite3로 옮기는 것도 같은 모듈 안의 일이다.
2. 백엔드의 Node 주 버전을 24로 고정하고, 시작할 때 `node:sqlite`를 불러오지 못하면 분명한 오류를 낸다.
3. 백엔드를 Electron 안의 Node(`ELECTRON_RUN_AS_NODE`)로 돌리기로 바꾸면, 그 Electron의 Node 버전에서 `node:sqlite`가 되는지 다시 본다.

## 4. 계획에 반영할 것

1. **PLAN 7절 P0 표의 E8:** "끝남. `node:sqlite`(Node 24 내장)를 쓴다. 저장소 모듈 안에 가둔다"로 바꾼다.
2. **BRIEF "정한 것"의 기술 구성:** SQLite 옆에 "Node 24 내장 `node:sqlite`"를 적는다.
3. **저장소 설정:** `journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 2000`, 표는 STRICT로 만든다. 트랜잭션은 작은 도우미 함수로 감싼다.
